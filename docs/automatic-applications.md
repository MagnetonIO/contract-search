# Automatic applications

The existing Contract Desk app has an authenticated Automatic applications view. Screening, browser work, private résumé versions, receipts and email outcomes use the existing private workspace. It starts paused and requires confirmed reusable applicant answers, a PDF résumé and a verified browser integration check before it can be enabled.

## Operation

- Start automation enables the schedule and requests an immediate durable run; the page shows the start receipt separately from worker activity.
- Browserbase owns the saved browser context; users enter logins and MFA in its private live view. Secrets are not supplied to the language model. LinkedIn, Dice, Indeed and Glassdoor sign-in buttons open their login pages in that context. The private `/browser-login` viewer shows active/saving/saved/expired states and handles Live View disconnects. Google/Apple popups appear as tabs in the viewer: newly opened sign-in tabs are selected automatically, manual selections persist, and closing a popup returns to the remaining site tab. Only tab titles and origins are shown; OAuth callback queries stay in the remote browser. Each login lasts up to 15 minutes. Saving checks for visible signed-in evidence and keeps inconclusive logins open; Close and keep session ends one explicitly. The next session waits for provider completion so cookies persist. a connected browser alone never establishes account authentication. Opening sign-in pauses automation. After saving a new site login, Start automation (or the next enabled scheduled run) automatically requeues authentication-only pauses once, with a fresh budget reservation. Existing submission intents never auto-retry.
- The hosted visual worker receives a fresh Browserbase screenshot for each decision and uses mouse navigation plus verified native input/upload helpers. It runs in Vercel Workflow without a laptop connection. Only the latest screenshot is retained privately per attempt; bounded action history and a private screenshot link appear under Application results. Passwords, MFA, human checks, unsupported eligibility answers and new agreements remain exceptions. Coordinate clicks cannot bypass final-submit or answer checks.
- AI SDK uses `openai/gpt-5.4-mini` for five-job professional-fit batches, mandatory qualification reviews, and screenshot-based browser decisions; the lightweight final filled-answer check uses `openai/gpt-5.4-nano`. Fixed pay, C2C, and US-location rules run in code, outside model scoring.
- Workflow checkpoints batches and individual applications. A global lease serializes cycles. Each attempt and final submission intent is claimed with conditional writes. Browser steps never replay automatically after failure.
- Up to 20 attempts per Chicago weekday, 8am–6pm. First run attempts one application; subsequent runs allow five until five confirmed submissions, then twenty.
- The automation allowance is $50/calendar month, including a conservative $20 browser subscription reservation. Each screening batch reserves $0.10; each application reserves $2.50. Known usage settles reservations. Unknown provider charges retain their reservation. Resuming an exception reserves a new attempt allowance.
- Unknown rate and C2C are accepted. Explicit W2-only, incompatible location, low advertised hourly rates, prior submissions and persistent dispositions are excluded. Fit requires score 80, compatible US-remote evidence, and verified qualifications. Unconfirmed location or qualifications are held separately from poor-fit skips. Interviews and higher offered pay do not lower professional fit.
- The collector exports `job-content.json` separately from the browser snapshot. Full descriptions stay private. Decisions are cached by content, facts, policy and disposition/stage.
- Résumé tailoring adds relevant verbatim highlights and preserves the master text and dates. Each attempt stores immutable PDF versions. Changed master PDFs require a matching canonical text source for tailoring; otherwise the approved PDF is used unchanged.
- The visual worker uses native helpers for verified text/select answers and the hosted file chooser for résumé uploads; unsupported controls, CAPTCHAs, new agreements and unknown required answers become exceptions. This is not a guarantee that every job board or ATS form can be completed.
- Every scored match receives an independent mandatory-requirement check before browser work. Required durations, residency and named tools need verbatim verified evidence. Resolved application URLs are claimed across records to prevent cross-board duplicate submissions.
- Vercel invokes `/api/cron/applications` hourly at minute 27 on weekdays; the engine enforces the Chicago work window and global lease. The dashboard uses the same open-opportunity population as the sidebar, with searchable per-job reasons, held/skipped counts, recent activity, and a private live browser link during application work. Secondary roles, submitted and dismissed records are outside that denominator.
- Closed postings receive a persistent closed disposition. Confirmed submissions become Applied. Ambiguous submission results are never silently retried. Results appear in the next morning digest.

## Credentials and local use

`python3 scripts/configure_ai_gateway.py` validates a hidden key, writes it to the native credential store (service `contract-search`, account `AI_GATEWAY_API_KEY`) and installs the Vercel production secret. The hosted app can also authenticate through Vercel OIDC. No key is embedded in browser code or résumé files.

Start locally with `python3 scripts/run_dashboard.py`; it loads the AI key from the native vault into process memory. Add `--hosted-data` to use the existing private hosted workspace; the local username/password gate remains required. Next.js runs on Node 24. `npm --prefix web test`, `npm --prefix web run typecheck`, `npm --prefix web run build`, and `.venv/bin/python -m unittest discover -s tests -v` validate the app and collector. Python credential helpers use macOS Keychain, Windows Credential Manager, or Linux Secret Service/KWallet, and refuse plaintext vault backends.

The opt-in integration test uses real Browserbase and model calls with synthetic applicant data and an intercepted employer form: `LIVE_AUTOMATION_TEST=1 node --env-file=.env.local web/scripts/test-application-browser.mjs`. It verifies screenshot decisions, mouse clicks, a file input created on demand, native PDF upload, confirmation tracking and duplicate prevention. It never submits to an actual employer. The separate first real application remains a live canary and must produce an actual employer confirmation before being reported as submitted.

The separate live-viewer test runs in an isolated Browserbase session: `cd web && LIVE_BROWSER_TEST=1 node --env-file=../.env.local scripts/test-login-viewer.mjs`. It verifies a synthetic authentication popup, automatic and manual tab selection, return when the popup closes, and provider completion before the closed view. It does not sign into any real account.
